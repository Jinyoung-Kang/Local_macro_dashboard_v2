# 아키텍처

## 1. 왜 세 개의 프로세스인가

구버전은 Streamlit 앱 하나였습니다. 그 구조의 문제는 명확했습니다 — **사용자가
화면을 열 때 수집이 시작**되므로, 캐시가 만료된 순간 접속한 사람이 전체 수집
시간(메뉴당 수십 초)을 그대로 기다렸습니다. 구버전도 이 문제를 알고 수집기를
별도 프로세스로 분리했고(`collector.py` + SQLite), v2는 그 분리를 **서비스
경계**로 굳혔습니다.

| 프로세스 | 언어 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| Collector | Python | 외부 소스 수집·파싱·적재, 키가 필요한 실시간 조회 | 분석, 화면용 가공 |
| Backend | Java | 저장본 읽기, 분석·판정, 인증, 캐시 | 외부 시장 데이터 직접 수집 |
| Frontend | TypeScript | 표시, 입력 | 계산 |

이 경계 덕분에:

- 수집기가 죽어도 **화면은 저장본으로 뜹니다.**
- 백엔드가 재시작돼도 수집은 계속됩니다.
- 키는 수집기 한 곳에만 있습니다(AI 키만 백엔드).

## 2. 데이터 흐름

```
외부 소스 ──▶ Collector ──▶ PostgreSQL ──▶ Backend ──▶ Redis 캐시 ──▶ Frontend
                  ▲                           │
                  └───── 수집 요청 (auto 모드) ─┘
```

`auto` 모드에서 백엔드는 저장본이 오래됐다고 판단하면 수집기에 **해당 태스크만**
실행을 요청하고 다시 읽습니다. 수집이 실패하면 오래된 저장본이라도 돌려줍니다 —
외부 장애 때 화면이 비는 것보다 낫고, 화면에는 수집 시각이 함께 표시되므로
오해의 여지가 없습니다.

## 3. 저장 스키마

| 테이블 | 용도 | 구버전 대응 |
|---|---|---|
| `snapshots` | 데이터셋별 "최신 상태" 1건 (JSONB) | 동일 |
| `timeseries` | (데이터셋, 시리즈, 날짜) → 값 | 동일 |
| `observations` | (데이터셋, 날짜, 엔티티) → JSON 레코드 | 동일 |
| `collector_runs` | 수집 실행 로그 (PID·heartbeat) | 동일 |
| `collector_task_runs` | 태스크별 결과 (상태·소요·실패 이유) | 동일 |
| `refresh_requests` | 수동 새로고침 기준 시각 | 구버전은 프로세스 전역 변수 |

`refresh_requests`가 새로 생긴 이유: 구버전은 이 값을 Streamlit 프로세스의 전역
변수(`_refresh_token`)로 들고 있었습니다. 화면과 백엔드가 분리된 지금은 프로세스
메모리에 둘 수 없어 공유 테이블로 옮겼습니다.

### 왜 JSONB인가

구버전은 pandas DataFrame을 JSON 문자열로 저장하면서 **dtype을 따로 실어야**
했습니다. 그러지 않으면 `"069500"` 같은 종목코드가 int로 추론돼 앞자리 0이
사라졌기 때문입니다(실제로 있었던 버그). v2는 데이터셋마다 **명시적 JSON 계약**을
두고 종목코드를 처음부터 문자열 필드로 정의합니다. 그래서 그 위험 자체가 없습니다.

## 4. 계산은 어디서 하는가

| 계산 | 위치 | 이유 |
|---|---|---|
| 파싱·정규화·단위 환산 | Collector | 원본 형식을 아는 곳에서 한 번만 |
| 등락률·국면·COT Index | Collector | 시계열 전체가 필요하고 적재 시점에 확정됩니다 |
| 수익률 매트릭스·모멘텀 순위 | Backend | 화면이 기간을 바꿔 가며 요청합니다 |
| 13F 분기 대비 액션·교집합 | Backend | 기관 조합이 요청마다 달라집니다 |
| 스프레드·백분위·해석 임계치 | Backend | 화면과 AI 리포트가 **같은 값**을 봐야 합니다 |
| 표시 서식 | Frontend | 로케일·색상 규칙은 표시의 문제입니다 |

구버전은 화면 코드(`views/*.py`)가 직접 계산했습니다. 그래서 같은 수치를 AI
리포트가 다르게 말할 여지가 있었습니다. v2는 계산을 백엔드로 모아 그 여지를
없앴습니다.

## 5. 캐시 전략

Redis는 **응답 캐시**입니다. 원본은 항상 PostgreSQL에 있으므로 캐시가 비어도
정확성에는 영향이 없습니다.

| 데이터 | TTL |
|---|---|
| 장중 시세성 (매크로 카드·수급) | 60초 |
| 일별 확정치 (FRED·KRX·섹터) | 5분 |
| 분기 공시 (13F) | 30분 |

## 6. 인증

사용자 계정 체계가 없는 1인용 대시보드라 구버전의 "비밀번호 한 개" 모델을
유지합니다. 다만 프런트·백엔드가 분리됐으므로 서명된 토큰(JWT)을 **httpOnly
쿠키**로 내려 브라우저 스크립트가 읽지 못하게 합니다. 비밀번호 비교는
`MessageDigest.isEqual`로 상수 시간에 수행합니다.

## 7. 장애 시 동작

| 장애 | 결과 |
|---|---|
| 수집기 다운 | 화면은 저장본으로 동작. 상태 화면에 "수집기에 연결하지 못했습니다" |
| Redis 다운 | 캐시만 없어짐. DB에서 직접 읽어 계속 동작 |
| PostgreSQL 다운 | API가 실패합니다. 이 계층만 가용성이 필수입니다 |
| 외부 소스 다운 | 수집 태스크가 `empty`/`error`로 기록되고 **기존 저장본은 유지** |
| 모든 수급 소스 다운 | 누적 이력으로 대체 + 화면에 날짜와 경고 표시 |
